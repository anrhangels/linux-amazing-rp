# Диагностика для разработчиков

## Установленный факт и открытый вопрос

В историческом отчёте зафиксировано чтение свободной памяти в `aggmain.asi +0x13C2F80`: исключение `0xC0000005`, адрес `0x01F74000`, состояние `MEM_FREE`. Предыдущее доступное DWORD находилось по `0x01F73FFC`; указатель увеличивался на четыре. Причина выбора диапазона и ожидаемое условие остановки остались неизвестны.

Это описание конечного недопустимого доступа. Оно само по себе не устанавливает use-after-free, ошибку размера, намеренную блокировку Wine или дефект конкретного API. Для таких выводов нужна история происхождения указателя и памяти.

## Адреса и сопоставление сборок

Абсолютный адрес зависит от раскладки памяти. Для точки исключения записывайте имя модуля, его SHA-256, базу загрузки, адрес инструкции и RVA (`адрес инструкции − база модуля`). Смещение `+0x13C2F80` имеет смысл только в контексте исследованного образа; у нового клиента код может находиться иначе.

Отдельно фиксируйте адрес операнда, тип доступа, размер чтения и состояние региона. RVA инструкции и адрес читаемых данных — разные величины. `MEM_FREE` в момент исключения не доказывает, что этот регион никогда не выделялся.

## Минимальный полезный захват

Нужны поток и время исключения, регистры, дизассемблирование вокруг инструкции, карта соседних регионов, стек, список модулей с базами и хешами файлов. Сохраните исходное исключение до вторичных ошибок обработчика. При повторном запуске сравните сигнатуру, а не только последнюю строку журнала.

В старой работе получены последовательная трасса из 22 866 инструкций и объединённый захват из 31 058 инструкций. Эти числа перенесены из итогового отчёта; файлы трасс удалены и здесь не приложены. Нельзя повторно проверить их полноту или восстановить из них код по одному этому описанию.

## Особенности загрузчика

В исследованном `aggmain.asi` некоторые секции заполнялись при исполнении и не содержали соответствующих raw-данных в PE на диске. Для анализа выполнявшегося кода нужен образ памяти с правильной базой, картой секций и временем захвата.

В одном зафиксированном процессе порядок был `amazing.exe → vorbisfile.dll → vorbishooked.dll → azmp.dll → aggmain.asi`. Не переносите порядок из стороннего разбора на другую сборку без сверки.

Ранний сбой под отладчиком совпадал с TLS-callback. Отладчик менял наблюдаемое поведение; раннее подключение и поздний захват требуют отдельных контрольных запусков без отладчика. Результат под отладчиком нельзя автоматически считать исходным сбоем обычного запуска.

Найденный вызов `wine_get_version` по контексту относился к TLS/ALPN-коду libcurl Schannel. Одна такая ссылка не доказывает намеренную блокировку Wine. Число `0xC1840B06` в разобранной операции соответствовало NAND; трактовка его как размера буфера не обоснована.

## Следующий содержательный эксперимент

1. Повторить стабильное исходное падение и сохранить бинарную идентичность клиента. Без этого новый анализ может относиться к другой проблеме.
2. Получить сравнение с Windows на том же клиенте. Отмечать различия API/выделений до момента расхождения, а не сравнивать только конечные стеки.
3. В Wine проследить выделение, отображение, изменение защиты и освобождение региона, из которого получен исходный указатель. Записывать размер, поток и вызывающий модуль. Выбрать узкий диапазон событий, чтобы не потерять полезные данные в шуме.
4. Выяснить, должен ли обход останавливаться по длине, маркеру, доступности страницы либо другому условию. До восстановления условия не предлагать «исправление» постоянным выделением страницы по адресу падения.
5. Если найдено различие семантики Wine/Windows, сделать минимальный самостоятельный тест соответствующего API. Проверять изменение Wine сначала на нём, затем на неизменённом клиенте.

Это план, а не выполненная часть исследования. Искусственное скрытие исключения или пропуск инструкции не подтверждает корректность игры: может лишь перенести повреждение данных дальше.

## Диагностическая сборка Wine

Исторически готовился Wine 11.0 с дополнительным журналированием выделений/освобождений, memory views и исключений. `configure` завершился, начался `make -j6`; сборка остановлена до завершения. Исполняемого runner'а, проверенного патча и результатов игрового запуска нет.

Для нового опыта сохраняйте commit исходников, toolchain, configure options, патч и полный build log. Сначала проверьте сам runner простой x86-программой и обычным приложением. Только затем переносите его в игровой эксперимент. Незавершённая компиляция ничего не говорит о работоспособности предложенной диагностики.
