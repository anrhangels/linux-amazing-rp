# Amazing RP: проверенный локальный запуск, 9 ноября 2026

> **Снимок исходников экспериментального локального профиля.** Это не установщик игры и не готовый Wine-префикс. Проверены конкретные GE-Proton11-11, DXVK и уже подготовленные native .NET/WMF/AmazingService. При простом клонировании репозитория эти компоненты и приватные резервные копии/манифесты не появляются. Готовые DLL и пользовательские данные здесь не распространяются.


## Запуск

```bash
amazing
```

Равнозначно: `~/.local/bin/amazing-compat`. Существующий ярлык **Amazing RP** использует обновлённую команду. В официальном лаунчере нажмите «Играть». Запуск направляется на рабочий стол 1 без переключения и запроса фокуса.

Подтверждены работа официального лаунчера, загрузка настоящего игрового клиента, подключение к серверу GREEN, трёхмерный мир и форма авторизации/регистрации с кириллицей. Пароли не вводились; управление персонажем после входа и длительная игровая сессия ещё не проверены. Если сервер разорвал соединение на форме входа, используйте «Переподключиться».

## Автоматический выбор экрана

Скрипт определяет монитор, к которому относится рабочий стол 1; если он ещё не существует, выбирает активный монитор. Разрешение, масштаб и текущая частота читаются из Hyprland. Перед запуском выбранный подключённый выход назначается основным **для текущей сессии Xwayland**. Это общий признак X11: другие X11-приложения могут учитывать его, пока игра работает. Физические режимы, расположение экранов, масштаб и конфигурация Hyprland не изменяются.

По завершении скрипт восстанавливает прежний основной выход, включая случай, когда основной вообще не был назначен. Если пользователь сам сменил основной выход во время игры, скрипт сохраняет его выбор. Восстановление проверено при закрытии предыдущего запуска.

Окно игры (строго класс steam_app_99998712 и заголовок AMAZING ONLINE) получает запрос полноэкранного режима без активации. Наблюдение работает всё время жизни лаунчера, поэтому можно нажать «Играть» позднее или перезапустить клиент из того же лаунчера.

Проверено на HDMI-A-3: **1920×1080, монитор около 165 Гц**, без прежних чёрных полос справа и снизу. Частота монитора не равна гарантированному FPS. При следующем запуске после смены монитора параметры определяются заново; перенос уже работающей игры между мониторами и hotplug не проверены. Выбор сохранён в `~/.local/state/linux-amazing-rp/last-screen.json`.

Виртуальный рабочий стол Wine испытывался, но не используется: в данном окружении он ограничивал режимы и сообщал 60 Гц.

## Исправления совместимости

1. **shell32 → shcore.** В отдельном тестовом префиксе экспорт CommandLineToArgvW направлен на небольшую обёртку, вызывающую настоящую реализацию shcore. Причина подтверждена GDB: клиент читал PE AddressOfFunctions напрямую и исполнял строку перенаправления как инструкции. Три сравнения с прямым вызовом shcore, включая кириллицу, кавычки и пустой аргумент, прошли.
2. **Поиск таблицы Direct3D9.** Клиент ищет машинную последовательность C7 06 ... 89 86 ... 89 86, отсутствующую в данных сборках DXVK/WineD3D, затем читает за пределами DLL. В приватной копии DXVK добавлена запись для этого механизма поиска, указывающая на реальную таблицу IDirect3DDevice9. Адрес измерен через штатный CreateDevice, привязан к SHA256 исходной DLL и корректно перемещается загрузчиком. Два созданных устройства подтвердили совпадение всех проверенных адресов; методы не заменены, экспорты/импорты DXVK сохранены.
3. Сохранена узкая конфигурация Wine relay для ntdll.RtlAllocateHeap и ntdll.ZwQueryInformationProcess из aggmain. Она позволяет пройти раннее m; его исходная причина отдельно не установлена. Подробные каналы seh/loaddll отключены в обычном скрипте, но минимальный relay остаётся частью проверенного окружения.

Это локальная совместимость с конкретной проверенной сборкой, а не универсальный установщик. После обновления Proton/DXVK нужна повторная проверка; адрес таблицы нельзя переносить между версиями. Защищённые файлы игры не патчились.

## Файлы

- Префикс: `~/Games/amazing-rp/ge11-clean-prefix`.
- Приватный вариант Proton: `~/.local/share/linux-amazing-rp/runners/GE-Proton11-11-Amazing-Compat`.
- Общий GE-Proton11-11-x86_64 и Arizona не изменены. Приватный вариант ссылается на общий runtime и содержит собственную копию графической DLL.
- Скрипт и исходники обёрток/проб: текущий каталог `compat-20261109`.
- Обычный журнал: `~/.local/state/linux-amazing-rp/logs/amazing-compat.log` (доступ только владельцу; ограниченная ротация при запуске).
- Подробные доказательства: `~/.local/state/linux-amazing-rp/autonomous-research/`.

Журналы лаунчера могут содержать токены. Не публикуйте их, готовый префикс, снимки памяти или DLL без отдельной проверки. Учётные данные автоматически не создавались.

## Откат

Закрывает тестовую сессию Amazing, восстанавливает исходные DLL и прежний ярлык/команду:

```bash
python3 ~/.local/share/linux-amazing-rp/compat-20261109/restore.py --restore-original
```

Скрипт проверяет хеши перед заменой и отказывается затирать неизвестные изменения. Резервная копия прежней команды — `amazing.before-compat`. Исследовательские материалы и отдельный вариант runtime сохраняются. Старый исходный префикс и данные клиента не очищаются.

## Обновление скриптов на уже подготовленном компьютере

Сначала закройте игру и лаунчер. Эти команды обновляют только исходники установленного рабочего профиля; не создают чистое окружение и не пересобирают DLL:

```bash
git -C "$HOME/linux-amazing-rp" pull --ff-only
cd "$HOME/linux-amazing-rp/tools/compat-20261109"
install -m 700 run.py screen.py restore.py stop-test-prefix.py "$HOME/.local/share/linux-amazing-rp/compat-20261109/"
install -m 700 launch.py "$HOME/.local/bin/amazing-compat"
install -m 700 amazing "$HOME/.local/bin/amazing"
```

Путь `$HOME/linux-amazing-rp` — пример расположения клона. Нужны существующие `ge11-clean-prefix`, приватный совместимый runner, native .NET/WMF и сохранённые JSON-манифесты в `~/.local/state/linux-amazing-rp/autonomous-research/`. `run.py` проверяет хеши перед запуском. Если компонентов нет, не копируйте случайные DLL: сначала требуется отдельно подготовить и проверить окружение.

`build-*.py` — исходники локальных генераторов совместимости. Они создают новые файлы в локальном кэше и метаданные исследования; автоматически ничего не устанавливают. `restore.py` требует исходные локальные резервные копии. C#-пробы проверяют семантику настоящих API; снимки памяти, клиент и бинарные результаты в репозиторий не входят.
